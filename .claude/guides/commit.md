# Commit 规范指南

## 核心原则：代码与文档同步提交

**每次 commit 必须同时包含对应的文档更新。** 代码变更若没有文档跟进，文档就会逐渐与代码脱节，成为误导用户的负担而非帮助。

## 文档更新要求

### 何时需要更新文档

以下任意情况发生时，对应文档必须同步更新，不得分开提交：

- 新增功能、指令、配置项
- 修改已有功能的行为或接口
- 删除功能、指令、配置项
- 修改配置项的默认值或取值范围
- 新增或删除插件
- 改变模块职责或文件结构
- 修复影响用户可见行为的 Bug

### 文档更新的两种形式

1. **更新已有文档**：找到描述该功能的现有文档段落，直接修改为与代码一致的内容。
2. **新建文档**：若涉及全新的模块、插件或功能领域，在对应目录下新建 README 或在 `.claude/guides/` 下新建指南文件。

### 不需要更新文档的情况

- 纯粹的内部重构（外部行为不变）
- 修复不影响用户可见行为的 Bug（如性能优化、日志调整）
- 测试代码的新增或修改

即使不需要更新，提交前也应主动确认：**现有文档是否仍与代码吻合**。若发现文档已有过时内容，顺手修正。

---

## 文档质量标准

文档的目标是：**用户只读文档，不读代码，也能清楚了解所有重要特性。**

### 必须覆盖的内容

每个插件或模块的文档至少包含以下要素：

| 要素 | 说明 |
|------|------|
| **简介** | 一句话说明该插件/模块的用途 |
| **触发方式** | 用户如何激活（关键词、指令等）|
| **功能特性** | 所有对用户可见的特性，逐条列出 |
| **使用流程** | 典型交互示例，包含用户输入和机器人响应 |
| **特殊指令** | 所有支持的斜杠指令或特殊关键词及其效果 |
| **文件结构** | 目录下各文件的职责说明 |
| **配置说明** | 完整的配置项列表，含字段名、默认值、说明 |
| **注意事项** | 限制条件、边界行为、潜在风险 |

### 文档写作要求

- **具体，不笼统**：写明实际的默认值、限制数值、触发关键词，而非"可配置""有限制"等模糊描述。
- **示例优先**：对复杂流程（如权限确认、多轮对话）务必提供完整的交互示例。
- **表格替代长列表**：配置项、指令、文件结构等信息用表格呈现，便于查阅。
- **保持与代码同步**：文档中的所有数值、字段名、行为描述必须与代码实现完全一致。

---

## Commit 前检查清单

在执行 `git commit` 之前，逐项确认：

- [ ] 本次变更涉及的所有文档是否已更新？
- [ ] 新增的功能/配置是否在文档中有对应描述？
- [ ] 删除或修改的功能是否已将文档中的旧描述移除或更正？
- [ ] 文档中的数值（超时、端口、限制等）是否与代码一致？
- [ ] 是否发现了与本次改动无关但已过时的文档内容？若有，顺手修正。

---

## Commit Message 格式

遵循项目约定，Message 使用中文，格式为：

```
类型: 描述

# 常用类型
功能   - 新增功能
修复   - Bug 修复
重构   - 不改变外部行为的代码重构
文档   - 纯文档更新
测试   - 测试相关
配置   - 构建/配置相关
```

若 commit 同时包含代码与文档，以代码变更的类型为主，无需单独拆分文档 commit。例如：

```
功能: CC 插件新增 /reload 指令，支持热重载配置

- 新增 handle_reload() 方法
- 更新 plugins/claude_code/README.md，补充 /reload 指令说明
```
